# at-modem-server

[![ci](https://github.com/milanomality/at-modem-server/actions/workflows/ci.yml/badge.svg)](https://github.com/milanomality/at-modem-server/actions/workflows/ci.yml)

Сервер на C++17, который слушает tty-устройство и отвечает на AT-команды,
притворяясь обычным модемом. Ответы задаются словарём ожиданий во внешнем
файле; шаблоны разбираются собственным матчером — **regex-библиотеки не
используются**.

Тестовое задание на вакансию «Разработчик C/C++, команда прошивки».

---

## Сборка

Нужны компилятор с C++17 и CMake ≥ 3.13. Внешних зависимостей нет.

```bash
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
```

Тесты:

```bash
ctest --test-dir build --output-on-failure
```

`ctest` прогоняет две группы: юнит-тесты матчера и словаря (`unit`) и
интеграционный тест, который гоняет собранный бинарник и сверяет байты
ответа (`integration`).

Сборка с санитайзерами:

```bash
cmake -B build-asan -DENABLE_SANITIZERS=ON && cmake --build build-asan -j
ctest --test-dir build-asan --output-on-failure
```

## Запуск

```bash
# на настоящем порту
./build/at-modem-server --device /dev/ttyUSB0 --baud 115200 --dict config/modem.dict

# на виртуальной паре pty (socat поднимается скриптом)
./scripts/run_socat.sh
# во втором терминале:
picocom -b 115200 --omap crcrlf /tmp/ttyClient

# без порта вообще — команды с клавиатуры
./build/at-modem-server --stdio

# проверить одну команду по словарю и выйти
./build/at-modem-server --dict config/modem.dict --dry-run 'AT+CPIN=1234'
```

### Ключи

| Ключ | Назначение |
|---|---|
| `-d, --device PATH` | tty-устройство |
| `-b, --baud RATE` | скорость, по умолчанию 115200 |
| `-f, --dict PATH` | словарь, по умолчанию `config/modem.dict`; `*.csv` разбирается как CSV |
| `--stdio` | работать через stdin/stdout вместо tty |
| `--no-echo` | стартовать с ATE0 |
| `--case-sensitive` | сопоставление с учётом регистра |
| `--cmee N` | форма выдачи ошибок: `0` — `ERROR` (по умолчанию), `1` — числовой код, `2` — текст |
| `--error TEXT` | ответ на нераспознанную команду при `+CMEE=0`, по умолчанию `ERROR` |
| `--dry-run CMD` | проверить команду по словарю и выйти |
| `--list` | показать загруженные правила и выйти |
| `-v / -q` | подробный лог обмена / только ошибки |

## Словарь ожиданий

Основной формат — текстовый, по строке на правило:

```
<шаблон>=<ответ>
```

Пример (`config/modem.dict`):

```
AT=OK
ATE[01]=OK
ATI=NDM Systems\r\nNDM-LTE-1000\r\n\r\nOK
AT+COPS?=+COPS: 0,0,"MegaFon",7\r\n\r\nOK
AT+CPIN\=[0-9][0-9][0-9][0-9]=OK
AT+CPIN\=*=+CME ERROR: incorrect password
```

Правила проверяются **сверху вниз, побеждает первое подошедшее** — значит
специфичные шаблоны нужно держать выше общих. Строки, начинающиеся с `#`
или `;`, и пустые строки игнорируются.

**Разделитель — первый неэкранированный `=`.** Это важно: `=` встречается и
внутри самих AT-команд (`AT+CPIN=1234`), поэтому в шаблоне его пишут как
`\=`. В ответе экранировать `=` не нужно — там он уже не разделитель.

В ответе разворачиваются `\r`, `\n`, `\t`, `\e`, `\0`, `\\`. Обрамление
`<CR><LF>` вокруг ответа сервер добавляет сам, в словаре пишется только тело.

Ошибку можно записать макросом `%CME <код>%` или `%CMS <код>%` — тогда её
вид определит текущий режим `AT+CMEE` (см. ниже), а не жёсткий текст:

```
AT+CPIN\=*=%CME 16%
```

| `+CMEE` | что уйдёт клиенту |
|---|---|
| `0` | `ERROR` |
| `1` | `+CME ERROR: 16` |
| `2` | `+CME ERROR: incorrect password` |

Литеральный процент пишется как `%%`; неизвестные макросы остаются в ответе
как есть. Жёсткий текст ошибки писать по-прежнему можно — он уйдёт клиенту
без изменений независимо от `+CMEE`.

Альтернативный формат — CSV (`config/modem.csv`, включается расширением
файла): `expect,answer` по RFC 4180. Там `=` в шаблоне экранировать не надо,
зато поля с запятыми и кавычками берутся в кавычки, а кавычка внутри поля
удваивается.

### Синтаксис шаблонов

| Конструкция | Значение |
|---|---|
| `.` | ровно один любой символ |
| `*` | ноль или более любых символов |
| `[abc]` | один символ из набора |
| `[0-9]`, `[a-fA-F]` | диапазоны внутри набора |
| `[^0-9]` | инверсия набора |
| `\.` `\*` `\[` `\\` `\=` | литеральный спецсимвол |
| всё остальное | литерал |

Совпадение всегда **полное**: шаблон обязан покрыть команду целиком, как
если бы стояли якоря `^` и `$`. Поэтому `AT` не совпадёт с `ATI`.

Сопоставление по умолчанию регистронезависимое (`at` = `AT`), как у
настоящих модемов; отключается ключом `--case-sensitive`. Регистр приводится
по ASCII, а не через `std::toupper`, чтобы поведение не зависело от локали.

Крайние случаи, соответствующие уточнениям из задания:

* `*` — это «ноль или больше любых символов», а не «ноль или один»:
  `A*E` совпадает с `AE`, `AbE`, `AbcdE` и `AbcdxyzE`, но не с `AbcdEx`.
* `[1,0]` из формулировки задания — это набор из трёх символов `1`, `,`, `0`.
  В рабочем словаре используется однозначное `[01]`.
* `]` первым символом набора и `-` последним трактуются как литералы —
  как принято в POSIX.

### Как устроен матчер

`src/pattern.cpp`. Шаблон один раз компилируется в вектор токенов
(`Literal` / `AnyChar` / `Star` / `Class`); символьный класс разворачивается
в `std::bitset<256>`, поэтому проверка вхождения — один бит, а регистр
учитывается ещё на этапе компиляции.

Сопоставление — итеративный проход двумя указателями с одной точкой
возврата: встретив `*`, запоминаем позицию, а при последующем несовпадении
откатываемся и отдаём звёздочке на один символ больше. Это корректно, потому
что между звёздочками стоят только односимвольные токены. Рекурсии нет,
стек не растёт, худший случай — `O(n·m)` при `O(1)` дополнительной памяти;
классический «катастрофический» для наивного backtracking вход
`a*a*a*a*a*b` против четырёх тысяч `a` отрабатывает мгновенно (есть тест).

## Поведение «модема»

Порт открывается в сыром режиме (`cfmakeraw`, `8N1`, `CLOCAL|CREAD`, без
`CRTSCTS` и без `IXON/IXOFF`, `VMIN=1`, `VTIME=0`). Канонический режим и
драйверное эхо выключены: построчную сборку и эхо AT-протокол делает сам, а
XON/XOFF съел бы служебные байты. Исходные настройки терминала сохраняются
и восстанавливаются при выходе, в том числе по `SIGINT`/`SIGTERM`/`SIGHUP`.

* Команда завершается `CR` (S3 = 13). Приходящий следом `LF` (S4 = 10)
  игнорируется, иначе на каждый Enter ответ уходил бы дважды.
* Ответ обрамляется по правилам verbose-режима: `<CR><LF>` + тело + `<CR><LF>`.
* `ATE1` / `ATE0` включают и выключают эхо (по умолчанию включено, как у
  модема после сброса). Строка самой команды `ATE0` ещё отражается — эхо
  гасится начиная со следующей.
* `ATQ1` / `ATQ0` подавляют и возвращают выдачу результатов.
* `A/` повторяет предыдущую команду (стандартное поведение Hayes).
* `ATS<n>=<v>` пишет, `ATS<n>?` читает S-регистр (значение выдаётся тремя
  цифрами, как у настоящего модема: `013`). Регистры `S3`, `S4` и `S5` —
  не декоративные: они и есть текущие символы конца строки, перевода строки
  и забоя, поэтому `ATS3=59` действительно делает `;` терминатором команд
  и меняет обрамление ответов. Номер и значение вне диапазона `0..255`,
  как и `ATS3` без `?` или `=`, дают ошибку.
* `AT+CMEE=<0|1|2>` переключает форму выдачи ошибок, `AT+CMEE?` её читает,
  `AT+CMEE=?` перечисляет допустимые значения. По умолчанию `0` — как
  предписывает 3GPP TS 27.007, то есть краткое `ERROR`.
* Backspace (S5 = 8) и DEL правят набираемую строку с корректным эхом
  `BS SP BS`.
* Пустая строка не вызывает ответа.
* Строка длиннее 1024 байт обрезается, и на её конце выдаётся ошибка.
* Нераспознанная команда → ошибка «operation not supported» (код 4), то есть
  `ERROR` при `+CMEE=0`.

### Составные командные строки

Расширенные команды можно перечислять через `;` — префикс `AT` пишется один
раз: `AT+CSQ;+CREG?`. Сервер выполняет их слева направо и склеивает ответ по
правилам протокола: информационные части идут подряд, а финальный код
результата один на всю строку.

```
AT+CSQ;+CREG?
+CSQ: 21,99

+CREG: 0,1

OK
```

Обработка **прекращается на первой же ошибке**, как у настоящего модема:
уже полученные информационные ответы уходят клиенту, а вместо `OK`
приходит код ошибки. Точка с запятой внутри двойных кавычек разделителем не
считается, поэтому `AT+CMGS="+7900;123"` остаётся одной командой.

Чтобы разделить ответ на информационную часть и финальный код, сервер
опознаёт стандартные результаты: `OK`, `ERROR`, `NO CARRIER`, `BUSY`,
`NO DIALTONE`, `NO ANSWER`, `CONNECT[ …]`, `+CME ERROR: …`, `+CMS ERROR: …`.
Одиночная команда этой обработке не подвергается — её ответ уходит ровно
таким, как записан в словаре.

Команды, меняющие состояние (`ATE`, `ATQ`), обрабатываются до обращения к
словарю, но ответ всё равно берётся из словаря — так текст ответа остаётся
настраиваемым. Если такой команды в словаре нет, отдаётся `OK`: отвечать
`ERROR` на успешно применённую настройку было бы неверно.

Порт — ресурс единоличный, поэтому сервер обслуживает одно соединение и
работает в одном потоке: `poll()` с таймаутом 200 мс, чтобы вовремя замечать
флаг остановки. Многопоточность здесь не дала бы ничего, кроме гонок за tty.

## Структура

```
src/pattern.{h,cpp}        матчер ограниченного синтаксиса регулярных выражений
src/dictionary.{h,cpp}     загрузка и разбор словаря (expect=answer и CSV)
src/serial_port.{h,cpp}    открытие tty, termios, чтение/запись, poll
src/modem_server.{h,cpp}   сборка командных строк, эхо, состояние, ответы
src/log.{h,cpp}            логирование в stderr
src/main.cpp               разбор аргументов, сигналы, точка входа
config/modem.dict          словарь по умолчанию
config/modem.csv           тот же словарь в формате CSV
tests/                     юнит-тесты и интеграционный тест
scripts/run_socat.sh       виртуальная пара pty для запуска без железа
```

Логи идут в `stderr`, а не в `stdout`: в режиме `--stdio` стандартный вывод
занят ответами «модема».

## Требования и проверка

Linux, компилятор с поддержкой C++17 (GCC ≥ 7 или Clang ≥ 6), CMake ≥ 3.13.
Внешних зависимостей нет; для `scripts/run_socat.sh` дополнительно нужен
`socat`.

CI (`.github/workflows/ci.yml`) на каждый push собирает проект под **GCC** и
**Clang** в Release и отдельно с **ASan/UBSan**, после чего прогоняет оба
набора тестов: 52 юнит-теста матчера, словаря, разбора цепочек, S-регистров
и макросов ошибок плюс 30 интеграционных проверок протокола на живом
бинарнике.
